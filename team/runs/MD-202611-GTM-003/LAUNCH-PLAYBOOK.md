# Midnight Dancer — Launch Playbook v1

Дата: 12.11.2026, Москва  
Статус: рабочий план до принятия владельцем. Не является разрешением на публикацию, реальные списания, письма площадкам или production-деплой.

## Главная логика

Не начинаем с одновременной публикации во все магазины. Сначала доказываем, что APK решает задачу танцора и не ломается на реальных устройствах. Затем подключаем один понятный денежный маршрут. После этого адаптируем сайт и отдельно проходим модерацию каждой площадки.

Главный стартовый маршрут:

**закрытая APK-бета → исправления → тестовая страница Pro → проверка оплаты и выдачи права → публикация Android → первые платные пользователи → iOS/Huawei как отдельные каналы.**

iOS сейчас не готова, поэтому её нельзя включать в первый технический gate.

## Что считаем запуском

Запуск Android v1 считается состоявшимся, когда:

- APK установили минимум 5 внешних тестеров;
- минимум 3 тестера завершили один полный сценарий: создать/открыть хореографию → тренировка → повторное использование;
- нет блокирующих дефектов установки, сохранения или тренировки;
- есть понятный Free → Pro оффер;
- один платёжный маршрут прошёл тестовый цикл: order → подтверждение → право Pro → отображение Pro в приложении;
- есть инструкция возврата/отмены и журнал событий;
- публикация выполнена только после отдельного разрешения владельца.

Цифры — рабочие ворота, а не доказательство спроса. Если пользователи не доходят до тренировки или не хотят Pro, запускаем новый цикл проверки, а не маскируем проблему рекламой.

## Реестр тестеров

Реестр ведём вне Git или в обезличенном файле владельца. В репозитории хранится только шаблон.

Минимальные поля:

| Поле | Пример |
|---|---|
| tester_id | T-001 |
| сегмент | salsa / bachata / caucasus / beginner |
| устройство | Android model, OS |
| APK build | 0.1.0-beta+12 |
| дата выдачи | YYYY-MM-DD |
| сценарий | freestyle / choreography / training |
| результат | pass / issue / blocked |
| проблема-ссылка | BUG-001 |
| готов повторить | yes / no |
| разрешил отзыв | yes / no |

Нельзя хранить в Git имя, телефон, email, паспортные данные, платёжные данные, токены и приватные отзывы без согласия. Для интервью можно использовать код T-001.

## Фазы и контрольные точки

### M0. Подготовка теста — 1–2 вечера

**Цель:** получить повторяемый тестовый пакет.

Сделать:

- определить текущую версию APK и известные ограничения;
- подготовить короткую инструкцию установки;
- подготовить 3 сценария: первый запуск, создание/редактирование хореографии, тренировка;
- завести обезличенный реестр тестеров;
- определить канал сбора отзывов;
- записывать модель телефона, Android, версию APK и шаг воспроизведения ошибки.

Выход:

- APK-файл и checksum;
- инструкция;
- форма/шаблон обратной связи;
- реестр T-001…T-005.

**Gate M0:** APK ставится хотя бы на твоём устройстве, тестовый сценарий понятен без устного объяснения.

### M1. Закрытая APK-бета — 5–7 дней

**Цель:** не рекламировать сырой продукт, а найти реальные поломки и ценность.

Порядок:

1. Выдать APK 2–3 знакомым танцорам.
2. Попросить пройти сценарий самостоятельно.
3. Через 24–48 часов спросить:
   - что получилось без помощи;
   - где остановился;
   - что было непонятно;
   - что реально захотел повторить;
   - за какую функцию готов платить.
4. Исправлять только блокирующие и повторяющиеся проблемы.
5. Дать обновлённую сборку ещё 2–3 тестерам.

Не просить «порекламировать всем» до подтверждения базового сценария. Просьба о рекомендации появляется после успешной тренировки и добровольного согласия.

**Gate M1:**

- 5 тестеров получили APK;
- 3 завершили полный сценарий;
- критических дефектов нет;
- минимум 3 повторяющиеся полезные реакции или чётко зафиксировано, что ценность не доказана;
- собраны 3 коротких отзыва с разрешением использовать их в маркетинге.

### M2. Проверка Free → Pro без публикации — 2–4 дня

**Цель:** проверить предложение до сложной интеграции магазинов.

Рекомендуемая гипотеза:

- Free: полный базовый фристайл и одна полноценная редактируемая хореография;
- Pro: несколько хореографий + отработка выбранного участка A–B с числом повторов, паузой и подготовительным отсчётом;
- предложение появляется при создании второй постановки или включении режима повторов, до начала тренировки;
- текущую тренировку не прерывать paywall-ом;
- существующие постановки и личные данные не удалять при окончании доступа.

На первом цикле можно показать «ранний доступ / готов обсудить Pro» и собрать намерение. Не объявлять цену окончательной, пока не будет хотя бы 3–5 разговоров и первых сигналов ценности.

**Gate M2:** минимум 3 подходящих пользователя понимают, за что Pro, и хотя бы один готов перейти к покупке/предзаказу. Если нет — меняем оффер, а не сразу добавляем функции.

### M3. Денежный контур Android — 3–7 дней

**Цель:** собрать один проверяемый маршрут оплаты.

Рекомендация для первого цикла:

- Android APK или публикация в RuStore;
- внешняя HTTPS-страница оплаты;
- провайдер, который письменно подтверждает работу с НПД и выбранным сценарием;
- серверная проверка платежа и единое право Pro.

Пока не делать четыре интеграции одновременно. Сначала один канал и один SKU.

Техническая последовательность:

1. Пользователь входит в аккаунт.
2. Сервер создаёт orderId, accountId, SKU, сумму, срок и канал.
3. Открывается разрешённый checkout.
4. Провайдер присылает webhook.
5. Сервер проверяет статус, сумму, валюту и orderId; повторное событие не дублирует право.
6. Сервер записывает entitlement: 'pro', 'paidUntil', 'channel', 'transactionRef'.
7. Приложение обновляет статус при возврате из оплаты и при следующем запуске.
8. При pending показывается «Проверяем оплату», а не мгновенное «куплено».

Существующий российский Apple-профиль не означает, что договоры продаж, банковские данные и разрешение внешней ссылки уже готовы. Huawei/AppGallery и Apple проверяются отдельными чек-листами. Подробные статусы и источники: [PAYMENTS-20261112](../MD-202611-GTM-002/PAYMENTS-20261112.md).

**Gate M3:** тестовый успешный платёж, отказ, задержка, повторный webhook, возврат и восстановление после переустановки пройдены в тестовой среде/допустимом режиме. Реальные списания — только после разрешения владельца.

### M4. Сайт оплаты и доверия — 2–4 дня

**Цель:** сделать одну страницу, которую можно адаптировать по каналу, а не строить отдельный сайт для каждой площадки.

Обязательные блоки:

- что делает Midnight Dancer;
- кому подходит;
- видео/скриншоты только с разрешением;
- Free и Pro без двусмысленности;
- цена, период, автопродление или отсутствие автопродления;
- условия отмены, возврата и поддержки;
- политика конфиденциальности;
- контакты продавца;
- кнопка оплаты только для разрешённого канала;
- статус заказа/инструкция восстановления Pro.

Внутри сайта использовать конфигурацию канала:

- 'direct_android';
- 'rustore';
- 'apple_ru';
- 'huawei_ru';
- позже другие страны.

Не показывать пользователю неподдержанный способ оплаты. Страница может быть общей, но юридический текст, валюта, кнопка и способ подтверждения должны зависеть от канала/региона.

Сайт для обмена и продажи пользовательских хореографий — отдельный продуктовый этап. В первый платёжный сайт его не смешивать: сначала доверие и Pro, затем каталог/маркетплейс.

### M5. Публикация Android — после отдельного разрешения

Порядок:

1. выбрать первый канал: прямая APK-бета, RuStore или другой доступный маршрут;
2. подготовить privacy, support, screenshots, description, content rating;
3. задекларировать внешний платёжный механизм там, где это требует площадка;
4. отправить на модерацию;
5. после одобрения проверить чистую установку;
6. выпустить ограниченный soft launch;
7. вручную отслеживать ошибки, активации, возвраты и обращения.

Не публиковать одновременно во все магазины: иначе при дефекте не поймём, где именно проблема — APK, магазин, платёж или entitlement.

### M6. iOS — отдельная ветка после готовности сборки

Условия входа:

- готова рабочая iOS-сборка;
- базовые сценарии повторены;
- выбран StoreKit или подтверждён применимый внешний маршрут;
- проверены Paid Apps Agreement, banking/tax и права аккаунта;
- подготовлены restore purchases, subscription states и Apple review notes.

Наличие российского профиля — плюс, но не автоматическое разрешение продаж. Сначала кабинет и договоры, потом код платежа, потом TestFlight, потом публикация.

### M7. Huawei/AppGallery — после Android-пилота

Условия входа:

- подтверждён merchant-допуск индивидуального разработчика из РФ;
- подтверждены банк, договор, IAP и/или внешний checkout именно для неигрового Android APK;
- подготовлена отдельная конфигурация канала;
- пройдены модерационные требования;
- проверены покупка, pending, возврат и восстановление права.

AppGallery — не «китайская копия RuStore». Для материкового Китая и Xiaomi/OPPO/vivo нужны отдельные исследования и договоры. Их нельзя автоматически включать в первый релиз.

## Еженедельный ритм при 60–90 мин/день

| День | Фокус |
|---|---|
| 1 | тестер/интервью и разбор одной проблемы |
| 2 | одна вайбкодинг-итерация по главному дефекту |
| 3 | повторная проверка APK и документация |
| 4 | один разговор о Pro/ценности |
| 5 | платёжный/сайтовый шаг или модерационные документы |
| 6 | резерв на фиксы |
| 7 | метрики и решение: продолжать / изменить / остановить |

Приоритет всегда один: **работающий сценарий → ценность → первая оплата → масштабирование каналов**.

## Метрики запуска

| Этап | Метрика | Решение |
|---|---|---|
| M1 | установка → первая тренировка | если низко, чинить onboarding |
| M1 | тренировка завершена | если низко, чинить core loop |
| M2 | понял Pro / готов обсуждать | если низко, менять оффер |
| M3 | checkout started → paid | если низко, проверять доверие/цену/платёж |
| M3 | paid → Pro active | если низко, чинить server entitlement |
| M5+ | 7-дневное повторное использование | если низко, не масштабировать рекламу |
| M5+ | возвраты/поддержка | если высоко, остановить расширение каналов |

## Что требуется от владельца

1. Дать актуальный APK и, когда можно, путь к исходникам.
2. Найти 5 тестеров из разных уровней/стилей.
3. Выдать APK и собрать обратную связь по шаблону.
4. Подтвердить желаемый первый Pro-пакет и ценовой тест.
5. Лично пройти merchant/магазинные договоры в защищённых кабинетах.
6. Не присылать в чат ключи, банковские данные и персональные данные тестеров.
7. После отдельного чек-листа дать разрешение на реальные подключения/публикацию.
8. После каждого gate сказать: продолжать, изменить гипотезу или остановить.

## Тикеты

- LAUNCH-M0: подготовить APK-beta kit и обезличенный реестр.
- LAUNCH-M1: провести закрытую APK-бету на 5 тестерах.
- LAUNCH-M2: проверить Free → Pro и текст предложения.
- PAY-M3: выбрать одного провайдера и подтвердить НПД-допуск.
- PAY-M4: реализовать server entitlement и тестовые webhook.
- WEB-M4: собрать канал-конфигурируемую страницу оплаты.
- STORE-M5: подготовить Android-публикацию.
- IOS-M6: довести iOS-сборку и проверить Apple sales status.
- HUAWEI-M7: подтвердить Huawei/AppGallery merchant/IAP/external checkout.
- MARKET-M8: только после первых оплат проектировать каталог продажи хореографий.

## Принцип остановки

Если после 5–10 подходящих тестеров никто не завершает тренировку или не видит ценности Pro, не увеличиваем рекламные расходы. Возвращаемся к продуктовой гипотезе, сегменту или формату функции.


## Дополнение: если знакомые танцоры в основном с iPhone — 12.11.2026

Это не блокер. Разделяем два вида проверки:

### Контур A — Android usability

Нужны минимум 3 реальных Android-устройства для проверки APK, звука, таймингов, сохранения и тренировки.

Источники:

- знакомый с Android;
- Android у партнёра/родственника тестера;
- танцор из локальной студии или Telegram-группы;
- временно одолженный телефон.

Эмулятор Android годится только для первичного smoke-теста интерфейса. Он не заменяет реальное устройство для аудио, уведомлений, производительности и жизненного цикла приложения.

### Контур B — iPhone demand/recruitment

Знакомые с iPhone всё равно полезны. На iPhone они могут:

- посмотреть короткое видео/демо;
- пройти интервью по боли и текущему способу тренировок;
- оценить Free → Pro предложение;
- оставить контакт на ранний доступ iOS;
- порекомендовать Android-пользователя;
- дать разрешённый отзыв о проблеме, а не о стабильности APK.

Их нельзя считать Android QA-тестерами и нельзя писать в маркетинге «приложение проверено на iPhone», пока iOS-сборка не готова.

### Практическое решение

Цель первой недели:

- 3 Android-тестера для работоспособности;
- 5–8 iPhone-танцоров для интервью и проверки спроса;
- минимум 3 контакта, готовых попробовать iOS после готовности сборки.

Таким образом, мы не откладываем продукт из-за платформы и одновременно заранее формируем очередь iOS-пользователей.
